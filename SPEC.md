# SPEC.md

# Ozon Seller Analytics

## 1. Цель проекта

Создать веб-приложение для аналитики Ozon-магазина.

Приложение должно помогать продавцу понимать:

* какие товары приносят прибыль;
* какие товары убыточные;
* сколько магазин реально зарабатывает;
* где теряются деньги: комиссии, логистика, возвраты, эквайринг, штрафы, удержания, себестоимость, налоги и прочие расходы;
* какие товары стоит масштабировать;
* какие товары нужно пересмотреть по цене;
* какие товары лучше отключить или не докупать;
* какие товары продаются, но фактически не дают чистой прибыли.

Главная идея продукта: показать не просто выручку, а **чистую прибыль по каждому товару / SKU**.

Приложение должно быть серьёзным аналитическим инструментом для продавца, а не игрушечным dashboard.

## 2. Технологический стек

Проект должен быть сделан на:

* Next.js;
* TypeScript;
* Tailwind CSS;
* App Router;
* Server Actions / Route Handlers для серверной логики;
* React Server Components там, где это уместно;
* Client Components только для интерактива;
* Zod для валидации данных;
* Prisma ORM для работы с базой данных;
* PostgreSQL как основная база;
* `@tanstack/react-query` версии `5.83.0`.

Обязательно использовать именно:

```json
{
  "@tanstack/react-query": "5.83.0"
}
```

`@tanstack/react-query` использовать для:

* клиентских запросов;
* загрузки таблиц;
* фильтров;
* пагинации;
* refetch;
* loading states;
* error states;
* синхронизации товаров;
* синхронизации финансов;
* mutations для сохранения себестоимости;
* mutations для расходов;
* mutations для настроек Ozon;
* invalidate/refetch после изменения данных.

React Query не использовать как глобальное хранилище состояния.

Для глобального состояния, если понадобится, использовать:

* React state;
* Context;
* URL search params.

Zustand добавлять только при реальной необходимости.

## 5. MVP

В первой версии нужно сделать MVP, а не огромную BI-систему.

MVP должен включать:

1. Базовую авторизацию или dev-user.
2. Подключение Ozon API.
3. Безопасное хранение Client ID и API Key.
4. Загрузку списка товаров.
5. Загрузку финансовых операций.
6. Таблицу товаров.
7. Карточку товара.
8. Ручной ввод себестоимости.
9. Расчёт прибыли по товару.
10. Dashboard по магазину.
11. Фильтры по периоду.
12. Управление общими расходами.
13. Сохранение данных в базе.

---

### 5.1 Порядок разработки: сначала моки, потом реальный бэкенд

MVP реализуется в две фазы.

**Фаза A — моковые данные, без бэкенда:**

* без PostgreSQL и Prisma;
* без реального Ozon API;
* пункты 2, 3, 5 и 13 из списка MVP откладываются до Фазы B.

Требования к мок-режиму:

* мок-данные должны быть реалистичными: 20–40 товаров, финансовые операции примерно за 60 дней, общие расходы;
* в моках обязательно должны быть товары всех статусов: прибыльные, убыточные, с низкой маржой и без себестоимости — чтобы проверить все состояния UI;
* весь доступ к данным идёт через отдельный data-слой `src/server/data/` с единым интерфейсом;
* UI, React Query hooks и функции аналитики не должны знать, откуда пришли данные;
* route handlers уже в мок-фазе имеют ту же сигнатуру и формат ответа, что и будущие реальные;
* изменения (себестоимость, расходы) в мок-фазе сохраняются in-memory на сервере — этого достаточно.

**Фаза B — реальный бэкенд.** Контракт будет описан в `api.md` (появится позже). После этого мок-реализация data-слоя заменяется на Prisma + PostgreSQL + Ozon API без переписывания UI и аналитики.

## 6. Визуальный стиль приложения

Стиль приложения должен быть премиальным, серьёзным, современным и выразительным.

Общее ощущение:

* тёмный графитовый фон;
* фиолетовые акценты;
* электрически-синие акценты;
* строгий интерфейс;
* ощущение дорогого аналитического продукта;
* максимально user friendly;
* серьёзно;
* остро;
* не игрушечно;
* не мультяшно;
* не кислотно;
* без лишней декоративности;
* не должно быть ощущения типового AI-generated интерфейса.

Приложение должно выглядеть как профессиональный инструмент для денег, прибыли и управления Ozon-магазином.

Интерфейс должен быть не просто рабочим, а визуально сильным: с характером, аккуратной композицией, хорошей типографикой, понятной иерархией и премиальным ощущением.

---

### 6.1 Фронтенд и UI-качество

При реализации интерфейса обязательно учитывать два направления качества:

#### `frontend-design`

Использовать подход `frontend-design` для создания выразительных интерфейсов, которые не выглядят как типовой шаблонный AI dashboard.

Цель:

* сделать интерфейс визуально самостоятельным;
* избежать ощущения “сгенерированной заготовки”;
* сделать дизайн премиальным и запоминающимся;
* добавить характер через композицию, spacing, карточки, акценты и визуальную иерархию;
* не копировать стандартные SaaS-шаблоны один в один;
* делать интерфейс современным, но не перегруженным.

Важно:

* каждая страница должна выглядеть законченно;
* dashboard должен сразу давать ощущение серьёзного продукта;
* таблицы не должны выглядеть как дефолтные HTML-таблицы;
* карточки метрик должны быть визуально сильными;
* кнопки, фильтры, инпуты и статусы должны быть приведены к единому стилю;
* интерфейс должен быть строгим, острым, уверенным.

#### `web-design-guidelines`

Использовать подход `web-design-guidelines` для аудита UI на доступность, читаемость и соответствие best practices.

Проверять:

* контраст текста на тёмном фоне;
* читаемость мелких подписей;
* размеры кликабельных элементов;
* hover / focus / active states;
* keyboard navigation;
* доступность форм;
* понятные ошибки в формах;
* корректные aria-label там, где нужны;
* логичную иерархию заголовков;
* отсутствие визуального шума;
* адаптивность;
* удобство работы с таблицами;
* понятность empty states;
* понятность loading states;
* понятность error states.

UI должен быть красивым, но не в ущерб удобству.

Главное правило: пользователь должен быстро понять, где деньги, где прибыль, где убыток и что нужно сделать дальше.

## 8. Интеграция с Ozon API

Реализуется в Фазе B, после появления `api.md`.

Интеграция должна быть только на сервере.

Нельзя вызывать Ozon API напрямую из браузера.

```txt
src/server/ozon/
```

Примерная структура:

```txt

  client.ts
  products.ts
  finance.ts
  analytics.ts
  schemas.ts
```

## 9. Ozon API client

Создать базовый Ozon API client.

Он должен:

* принимать `clientId`;
* принимать `apiKey`;
* добавлять нужные headers;
* делать POST-запросы;
* обрабатывать ошибки;
* возвращать типизированный результат;
* не использоваться в client components.

Примерная идея:

```ts
type OzonRequestParams<TBody> = {
  endpoint: string;
  body: TBody;
  clientId: string;
  apiKey: string;
};

async function ozonRequest<TResponse, TBody>(
  params: OzonRequestParams<TBody>,
): Promise<TResponse> {
  // server-only request
}
```

Ошибки Ozon API должны преобразовываться в понятные ошибки приложения.

```ts

  grossRevenue -
  totalOzonExpenses -
  totalProductCost -
```

## 27. React Query

Обязательно подключить React Query Provider на уровне приложения.

Примерная структура:

```txt
src/providers/
  query-provider.tsx
```

Provider:

```tsx
'use client';

import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { ReactNode, useState } from 'react';

export function QueryProvider({ children }: { children: ReactNode }) {
  const [queryClient] = useState(() => new QueryClient());

  return (
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  );
}
```

Использовать query keys централизованно:

```ts
export const queryKeys = {
  products: ['products'],
  product: (id: string) => ['product', id],
  dashboard: (period: string) => ['dashboard', period],
  expenses: ['expenses'],
  ozonSettings: ['ozon-settings'],
};
```

После mutations делать invalidate:

```ts
queryClient.invalidateQueries({ queryKey: queryKeys.products });
queryClient.invalidateQueries({ queryKey: queryKeys.dashboard(period) });
```

## 28. Синхронизация

Сделать серверные функции:

```txt
syncProducts(storeId)
syncFinanceOperations(storeId, dateFrom, dateTo)
syncAll(storeId, dateFrom, dateTo)
```

Синхронизация должна:

1. Получить настройки Ozon.
2. Запросить данные из Ozon API.
3. Нормализовать данные.
4. Сохранить в базу.
5. Обновить существующие записи.
6. Не создавать дубли.
7. Вернуть результат.

Тип результата:

```ts
type SyncResult = {
  success: boolean;
  productsCreated: number;
  productsUpdated: number;
  operationsCreated: number;
  operationsUpdated: number;
  errors: string[];
};
```

## 34. Важные бизнес-правила

### 34.1 Себестоимость

Если у товара нет себестоимости, прибыль по нему нельзя считать точной.

Такой товар должен быть помечен как:

```txt
Нет себестоимости
```

Но выручку и расходы Ozon всё равно можно показывать.

---

### 34.2 Возвраты

Возвраты должны уменьшать прибыль.

Если Ozon API отдаёт возвраты отдельными операциями, их нужно учитывать отдельно.

---

### 34.3 Комиссии и логистика

Комиссии, логистика, эквайринг и удержания должны быть отдельными полями, чтобы продавец видел, куда уходят деньги.

Не надо складывать всё в одно поле без детализации.

---

## 35. Что не делать в MVP

Не делать в первой версии:

* сложную BI-систему;
* много ролей пользователей;
* интеграцию с Wildberries;
* прогноз закупок;
* AI-рекомендации;
* импорт из Excel;
* графики по 20 метрикам;
* мобильное приложение;
* сложное распределение общих расходов по товарам;
* полноценную бухгалтерию;
* сложный складской учёт;
* многоуровневые права доступа.

Это можно добавить позже.

## 37. Главный результат MVP

После реализации MVP пользователь должен иметь возможность:

1. Подключить Ozon API.

## 39. Definition of Done

Пункты про базу, Ozon API ключи и синхронизацию относятся к Фазе B. Для Фазы A задача считается выполненной, если всё остальное работает на моковых данных через изолированный data-слой.

Задача считается выполненной, если:

* проект запускается;
* страницы открываются;
* данные сохраняются в базу;
* Ozon API ключи не попадают на клиент;
* товары можно синхронизировать;
* финансовые операции можно синхронизировать;
* себестоимость можно указать;
* прибыль считается;
* убыточные товары видны;
* товары без себестоимости видны;
* dashboard показывает основные метрики;
* расходы магазина можно добавить;
* расходы учитываются в общей прибыли;
* установлен `@tanstack/react-query` версии `5.83.0`;
* React Query Provider подключён на уровне приложения;
* клиентские запросы используют `useQuery`;
* клиентские изменения используют `useMutation`;
* после mutations выполняется корректный invalidate/refetch;
* UI выполнен в тёмном графитовом стиле;
* акценты приложения — фиолетовый и электрически-синий;
* интерфейс выглядит как серьёзный премиальный SaaS-продукт;
* интерфейс не выглядит игрушечным;
* код типизирован;
* нет критических TypeScript ошибок;
* нет явных runtime ошибок.
